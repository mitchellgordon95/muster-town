## 2. What is true today (verified in code and on the live town)

- **Reports already stop at the manager.** `submit_report` files the report in the building's in-tray (`intrayOf`, pending reports of that building) and the resident goes idle. Review is one text box and one button (`reply.ts`): a reply becomes the author's next assignment, an empty reply archives. Before step 1 the in-tray was worked by whoever the `reviewPolicy` setting said (`human` everywhere; `reviewer` ran a short session per report and was never used; `auto` acknowledged on arrival). Step 1 removed the setting (migration 029): the manager agent works the in-tray when the building has one, else the humans do.
- **The manager is the only conversational surface** (design review 5, 3c5914c): `messageAgent` refuses residents of a building with a manager; the proxy chat refuses residents outright. But a message to the manager still becomes a `Message from …` assignment that runs a desk session and ends in a report. There is no 1:1.
- **Goal-directed budgets are one third built.** Steps 1a–c shipped on 2026-10-21 (7bef911, 2eae49f, 441a7f3): `grants` and `key_results` tables (migration 025), the `Grants` service (`world.grantDesk`: draft, propose, fund/counter/reject, checkpoint continue/adjust/cut, close, key-result status, derived spend, exploration allowance), REST routes under `/api/grants`, and the board route returning the grant board. Not built: lanes and the `canStart` gate (step 2), the board UI and funding buttons (step 3), the key-results prompt block (step 4), the pilot (step 5). Every building was still `budgetMode: open` then; since 2026-10-28 (gr_glon8xr0io) the mode is gone and every lab is goal-directed.
- **The Town Hall has no in-tray and no manager agent.** Its furniture is mod station, bench, planning desk, schedule board, library, town map table, outbox, meeting table. Town-hall meetings invite every building's manager and reviewer agents plus the moderators (`defaultAttendees`); their notes go to the library and their decisions become assignments.
- **Meetings** have four kinds (standup, retro, planning, town-hall), a scheduler that starts `scheduled` ones, one-shot summaries and a tool-using facilitator. Kelly is researching how they work in practice (town hall decision 3); her report is an input to step 5 below.

## 3. The reconciliation

The budgets design put the human's surface on the **building board** (proposal cards, fund buttons, checkpoint buttons, an amber dot on the map). The waterfall moves the human's surface to the **Town Hall in-tray** and the **manager's 1:1**. The board stays, but as the residents' surface: the goal and key results they work toward. Everything else in the budgets design survives unchanged: the building goal, grants (since 2026-10-25: key results live on the goal and a grant is the plan for one of them, with a testing plan; `docs/goal-directed-budgets.md`, "Model change"), proposals that Mitchell funds, counters or rejects, the 100% checkpoint (the 50% one was removed 2026-10-27, mt_rjhwj2qggm), the three spend lanes and the gate, the exploration allowance, and `building.fund` as a human-only permission.

Three tiers, the same shape at each level:

| tier | who talks | what lands in the in-tray | who decides |
|---|---|---|---|
| Town Hall | Mitchell ↔ managers (1:1, town-hall meetings) | manager **rollups**, grant **proposals**, **checkpoints**, **escalations** | Mitchell: one text box, one button; Fund / Counter / Reject; Continue / Adjust / Cut |
| Building | manager ↔ residents (assignments, standups) | resident **reports** | the manager agent, in its team-lead session; escalates by rollup |
| Resident | nobody; works from assignments | — | — |

Drill-down is free if every rollup lists the reports it covers in its provenance (`sourceIds`): Town Hall in-tray → rollup → covered reports (DocView already renders sources) → report → session transcript. The building in-tray and filing cabinet are already readable by anyone, so "drill into a building" is walking to it, as now.

### 3.1 The autonomy rule (town hall decision 5) as code

- **No review-policy setting** (amendment a). Who works a building's in-tray is derived: if the building has a manager agent (`managerAgentId`, not stopped, banned or retired), the manager works it; else the humans holding `building.review` do, as today. Stopping the manager hands the in-tray back to the human: that, and the 1:1, is how Mitchell keeps control. Core: `managerAgentOf` and `intrayWorker` in `core/domain.ts`; the `reviewPolicy` column is dropped (migration 029) and the runtime's per-report reviewer session is gone.
- **The manager is a team-lead session** (amendment b), not a short review session per report. It is idle when nothing is pending. It wakes when a resident's report lands in its in-tray or when Mitchell opens the 1:1 (§3.4), with the context of what it assigned (its wiki and log, the team block, and the in-tray block below). In that session it reads each report, decides with `review` (approve, continue, redirect, stop), assigns follow-ups, and decides itself whether to wait for more reports or roll up. The manager does only decisions and rollups in that session (town hall 2026-10-25): any task that appears (verifying, writing, fixing) becomes an assignment at once, and independent tasks go to different residents in parallel rather than queued on one; this is a prompt rule (`managePrompt`), not a board rule. **Managers may assign work to themselves** (town hall 2026-10-25, decision 6): the default is to delegate, self-assignment is for what is small, blocking, or needs the manager's permissions. A self-assignment runs as a normal work session (desk, code, web), and its report lands in the building's own in-tray like a resident's, where the manager decides it in its next team-lead session (`review` allows a manager its own work report) and folds it into the rollup. Rule of thumb for the Town Hall: one rollup per day, or sooner on escalation. When it has nothing left to decide, the session ends and the manager goes idle. The manager's report at the end of such a session is a rollup when one is due (§3.2); otherwise there is nothing to file: an idle building is silent.
- **The in-tray block.** Every session of a manager agent gets, after its team block, `## Your in-tray` (`managerIntrayBlock`, `core/prompts.ts`): the residents' pending reports (id, author, verdict, age, their "What I need from you" line), the decision verbs, the escalation criteria below, and the rollup rule with the time of the last rollup and the count of reports decided since. It is the same block in a desk work session, in the team-lead session (step 2) and in the 1:1 (step 4).
- **Flags** (town hall 2026-10-25 evening: "plant a flag", Pix). A human's quick request to a building, outside grants and meetings: a short note (first line = title) planted from the UI (**⚑ Plant a flag** on the Town Hall in-tray with a building picker, or on a building's own in-tray) or `POST /api/buildings/:id/flags {text}` (human-only, like goal key results; needs `building.assign` on that building). It is a doc of type `flag`, state `building`, decision `pending`, filed in the building and listed in the building's in-tray with a `⚑ flag` badge (never in the Town Hall's); it wakes the manager's team-lead session the way a resident's report does and shows as a `FLAG` line in the in-tray block. The manager delegates it with `review` plus `assigneeId` (a resident of that building): `continue` makes the flag's text the resident's assignment verbatim, `redirect` makes the manager's note the assignment with the flag as context, `approve` marks it handled with no assignment; `stop` is refused (no agent to stop). No nearest-manager logic: the human picks the building. **Lane:** the assignment is `directed` in any building (`laneOverride: DIRECTED` in `decideFlag`), because a human asked for it, exactly as a decision of a meeting a human spoke in is directed; the manager only picks who. That keeps "agents can't create directed work" true (the manager can't plant a flag, and `assign` still needs a grant or exploration lane) while a flag runs even in a blocked building. Follow-ups from the flagged work's report inherit the directed lane as any continuation does. Why not exploration with the flag text as the gap: exploration is the agents' own gap-finding and is capped by the building's daily allowance, so a flag planted after the allowance is spent (the Workshop was at 10.1M of 5.4M on 2026-10-25) would be held until midnight, the opposite of a quick fix; and it would be the only case where a human's ask counts against the agents' allowance. If flags turn out to be abused as a budget bypass, the fix is on the human side (a per-day flag cap), not the lane.
- **Escalation criteria**, in the block: decide yourself unless the decision (a) changes the building goal or a key result, (b) spends money outside a funded grant or the exploration allowance, (c) needs a human in the real world (`request_human`), or (d) the report's author asks for something only a human can give (merge rights, a secret, a credential, a decision Mitchell reserved). Those go into the next rollup's "Needs from Mitchell", not to Mitchell directly, unless an outbox request or a grant proposal already carries them.
- **Notifications** (amendment d). A resident's report in a building with a manager agent notifies no human: its @-mentions reach agents only (`notifyMentions` with `agentsOnly`), and the HUD lists in-tray counts only for buildings a human works plus the Town Hall. A manager's rollup is a Town Hall item (§3.2) and notifies as before; its own work reports notify agents only, like a resident's. A general notification-subscription system is parked (town hall decision 4) until this rule proves too coarse.
- `AGENTS.md` non-negotiable 1 ("nothing continues without a decision") stays true one level down: nothing continues without the **manager's** decision, and the manager's work continues only through rollups, grants and checkpoints that Mitchell decides. Nothing self-starts meetings (amendment c): meetings are created by humans or by the scheduler on a building cadence, never by an agent verb.

### 3.2 Rollups and what the Town Hall in-tray holds

- **What:** a `report` doc by the manager, tagged `rollup`, filed in its building like any report, listed in the Town Hall in-tray while pending. `submit_report` takes `rollup: true` (managers only) and requires the covered reports in provenance `sourceIds` (each a report of the manager's building). Body (the town default since 1:1 mt_vcn0e66r1t, from town hall decision 5, dc_z4zgfk6tsz; example dc_55a4u8lzn4), one screen: an optional one-line intro (the live commit), then `## Shipped`: at most 3 numbered items, each with **What it is:** (plain words, ids after), **What you'd see:** (where in the UI, the live numbers), one cropped picture (≤300 px tall, at most 2 per rollup; API-only changes say so) and **Your call:** (one line, or "None"); `## Decided`: one line per covered report (id → decision); `## Key results`: a table, one row per funded grant's key result (status, spent / granted), plus the day's spend by lane; `## Needs from Mitchell`: at most two items, "Nothing needed" is valid, and only what has no other channel (1:1 mt_uf1bwd3exq; `ROLLUP_NEEDS_RULE`): a reserved decision, a question in words, a 1:1 invite, a real-world action with no outbox request. `submit_report` refuses a rollup whose Needs names a grant awaiting a human (proposed, checkpoint), an open outbox request or a pending Town Hall report, warns on more than two Needs list items, and appends a generated line at the end of Needs: "Already waiting in your in-tray: N proposals, M requests, K rollups" with their ids (that building's proposed grants, open requests and pending rollups at submit time), or "Nothing else waiting in your in-tray.". It refuses a rollup without the four headings and files one whose Shipped items lack the labels with `warnings` (old-style rollups still go through). The parser is `parseRollup` in `packages/schema/src/rollup.ts`; the Town Hall in-tray shows the Shipped items as cards when every item has the three labels, plain markdown otherwise.
- **Only rollups are Town Hall items** (decision 6, 2026-10-25; before it, every manager report was). A pending report tagged `rollup` (`isTownHallItem`; a checkpoint report is one) is listed in the Town Hall in-tray and not in the building's. Routing goes by what the report is, not by who wrote it: a manager's own work report, from a self-assignment, a meeting decision or a "Message from Mitchell" assignment, lands in the building's in-tray like a resident's, and the manager decides it in its next team-lead session and folds it into the rollup; what needs Mitchell goes in the rollup's "Needs from Mitchell". Nobody decides their own rollup (`review` refuses); a human does. Buildings without a manager agent put nothing in the Town Hall in-tray.
- **When:** the manager decides at the end of its team-lead session: roll up when a covered report hit an escalation criterion, or when 24 h have passed since the last rollup and something was decided. No rollup when nothing happened. A town-hall meeting also produces one per manager (the standup summary becomes the rollup's draft).
- **Decision on a rollup:** Talk to the manager (a 1:1, whose decisions become the manager's work) or Archive (1:1 mt_cz11aqe81a removed the reply box).
- **Reports Mitchell never sees by default:** the Town Hall in-tray shows only rollups, proposals, counters and checkpoints. The building in-tray keeps showing resident reports to whoever walks there, with a note that the manager works it.

### 3.3 Proposals and checkpoints

Unchanged in substance from the budgets design, moved in place: a `proposed` or `countered` grant and a grant at `checkpoint` are Town Hall in-tray rows with the same buttons the budgets design put on the board (Fund with a token field prefilled to the ask, Counter with a note, Reject; Continue, Adjust, Cut). `POST /api/grants/:id/decide` already exists. The manager proposes from a 1:1 or at the end of a review session ("if exploration findings are in and no proposal is open, draft one", as the budgets design says). The board keeps the read-only view for residents.

### 3.4 The manager's 1:1 (the channel)

- **What it is:** a conversation between one human and one manager agent with no assignment and no report. Mitchell can set or change the building goal there, ask what is going on, and hand the manager work, which the manager turns into assignments on the spot.
- **How:** reuse the meeting machinery. A meeting of a new kind `one-on-one`, building-scoped, attendees = [the manager], created in phase `discussing` (no summaries), the human as the only other speaker. The manager side is a host `runAgentSession` with town verbs and the manager's prompt blocks (memory, team), fed the human's utterances through the existing streaming input and interrupt path (Root's note dc_e8tgzb2t3b, section 1). Each turn the manager speaks through the `meeting` verb and may `assign`. Decisions recorded in the 1:1 become assignments through `meetingDecide`, as in any meeting. The human ends it (the typing guard already prevents an agent closing under a typing human); the notes doc is the transcript, filed in the building's cabinet. The 1:1 session spends the manager's budget; it runs on the host, so it can't edit code, which is right for a manager.
- **UI:** "Talk to ★ <manager>" on the agent and building panels opens the 1:1 (the meeting panel with the composer) instead of the message composer. A building without a manager agent keeps today's direct message. The `Message from …` assignment path stays for messages to visitors and to manager-less buildings.

### 3.5 The Town Hall in-tray

A new place in the Town Hall (`intray:town-hall`, furniture piece next to the planning desk) with the existing `IntrayPanel`, fed by `GET /api/buildings/town-hall/intray`, which since step 1 returns `{ reports, grants }`: the pending manager reports of every building (`intrayOf(town-hall)`), plus grants in `proposed`, `countered` or `checkpoint` (`grantsAwaitingDecision`). The Town Hall's badge count (`intrayCount`) is both together. Rows carry the building's name and sprite, expand to the covered reports, and offer the decision controls for their kind. The HUD shows its count the way building panels show theirs. Nothing else in the Town Hall changes.
