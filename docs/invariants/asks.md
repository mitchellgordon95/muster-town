# Invariants: asks

What must always hold for asks (`packages/core/src/asks.ts`, the `asks` table from migration 097). An ask is something only a human can do, stored and typed instead of parsed out of a report's prose. Each invariant names the test that proves it. The design is in [docs/legible-delegation.md](../legible-delegation.md) §3-4 (build steps 1-2 in §11), and the map is in [docs/architecture.md](../architecture.md#map-the-system-in-10-minutes).

**Citation format** (checked by `npm run check:docs`, see `scripts/check-doc-refs.ts`): each invariant has one or more lines like

- Test: `packages/core/test/asks.test.ts` › `only a human who can fund decides an ask; a deferred ask stays listed until decided`

The first code span is the test file. The second is the `it` text, copied exactly. If the file is missing or the text isn't in it, the check fails, so renaming a cited test means updating this doc in the same change.

## Invariants

1. **An ask is created in code where its source is created, never parsed later.** A grant proposal, a step report whose forecast projects past the ceiling, and a grant held at its checkpoint file a money ask on the grant (`Grants.event`, `fileForecast` and `Grants.checkpoints`; the last two fold into one, grants.md invariant 12); an asked retainer a money ask on its schedule (`askRetainer`); `request_human` a credential ask when it asks for a token or key, else a click (target the request); a captain ask and an access request a click. Each carries its type, target, building, record, title, body from the source's own words and the branches of its decision verbs.
   - Test: `packages/core/test/asks.test.ts` › `a proposal files one money ask; a second ask on its grant folds in as a source line; funding retires it with the event's text`
   - Test: `packages/core/test/asks.test.ts` › `a checkpoint, a retainer, an outbox request, a captain ask and an access request each file one ask, and the event that decides each retires it`
2. **One live ask per need** (invariant 20). A second ask on a need that already has an open or deferred card is refused at the door (`ask.folded`): no second ask is made, nothing is added to the card, its words are one entry on the thread, and the same words again write nothing.
   - Test: `packages/core/test/asks.test.ts` › `a proposal files one money ask; a second ask on its grant folds in as a source line; funding retires it with the event's text`
3. **The event that decides a target retires its live asks, with that event's text as `retiredBy`.** The hooks sit next to the state change, never on a timer: a grant funded, continued, adjusted, countered, rejected, cut, closed, withdrawn or stopping (`Grants.event`); access let in or declined; a captain ask accepted or declined; a request claimed, declined, withdrawn or deleted (`requestAction`); a retainer decided or ended; a key result whose status a human sets, or that is met or missed by anyone; and a reset account's pending requests. The deciding event retires the asks of the need it answers: a grant's or a retainer's event retires only its money asks and settles only its money need, so a credential, policy, click, do or meeting card on the same grant or retainer stays live (`retireAsks` `only`; dc_yvgkuk2mv1).
   - Test: `packages/core/test/asks.test.ts` › `a grant's or retainer's deciding event retires only its money asks: a credential or policy card on it stays live (dc_yvgkuk2mv1)`
   - Test: `packages/core/test/asks.test.ts` › `a checkpoint, a retainer, an outbox request, a captain ask and an access request each file one ask, and the event that decides each retires it`
4. **A manager's own ask on a target retires with it too.** An ask a manager files with `ask` on a grant, a retainer or a key result is on that target (on a grant or retainer: a money ask; invariant 3), so the event that decides the target retires it like the town's own card; nothing reads prose to find out an ask is moot (the old digest's regex and the rollup readers are gone).
   - Test: `packages/core/test/asks.test.ts` › `the event that decides a target retires every live ask on it, a manager's own ask included`
5. **Only a human decides an ask; nothing decides one by silence.** `decideAsk` and `deferAsk` need a human who can fund the ask's building or who captains the goal the ask moves (`askGoalId`) or a goal above it, refusing everyone else with 403 (`canDecideAsk`, gr_0vuiuqcw8p; a goal proposal's ask: whoever may edit the goal it lands on). The Town Hall in-tray routes every live ask by its own id with that same rule (`intrayRoutes`: `mine` when the viewer is its goal's captain, `canDecide` from `canDecideAsk`), and the web reads an ask's route by ask id first (`askRoute`, `packages/web/src/panels/queueOrder.ts`), so Mine holds only the viewer's subtree and a card the viewer cannot decide shows no buttons. `decideAsk` records who, when and what (the branch label, plus the human's optional note as "<label>. <note>", up to 2000 chars; the ask's building manager hears it in their inbox). A request's do ask decides through the request itself (no Claim since 2026-11-12: Done takes the report back, Decline a note; the text after this describes the old Claim note) (kept as `requestNote`, sent to the agent author with the claim), Decline a required one (the server refuses a bare decline); `deferAsk` (a human or the Secretary) parks an open ask behind an event, and it stays listed in the Town Hall in-tray's `asks` (and counted in its badge) until decided or retired. When the ask or target id it waits behind is decided or retired, it is open again (`reopenDeferred`, `ask.reopened`). A decided ask is final.
   - Test: `packages/core/test/asks.test.ts` › `only a human who can fund decides an ask; a deferred ask stays listed until decided`
   - Test: `packages/core/test/asks.test.ts` › `a deferred ask opens again when the ask or the target it waits behind is decided or retired`
   - Test: `packages/core/test/captain-asks.test.ts` › `decideAsk and deferAsk: the captain decides in the subtree, is refused (403) outside`
   - Test: `packages/core/test/captain-asks.test.ts` › `in-tray routes: every ask by its own id, Mine and canDecide from the same rule`
   - Test: `packages/server/test/asks.test.ts` › `a non-admin captain of a leaf goal decides a click ask from a building under it (200), and is refused one from another building (403) (gr_0vuiuqcw8p)`
6. **A manager's card is checked before it is filed.** `ask` (and `review` with `ask`) refuses, filing nothing, when a money ask names no grant or retainer or when a target does not exist (`checkAskCards` in `packages/core/src/asks.ts`). A card of a need's type on a target with an open need renders that need; a card of another type is a need of its own (invariant 20). A second render of the same need is refused at the door; only a town placeholder card is replaced, whole, by an author's card with a recommendation.
   - Test: `packages/core/test/asks.test.ts` › `a manager's ask: refused when a money ask names no grant or retainer, or its target is not one of this town; a second money ask on its grant is refused naming its card; one with no target is an ask of its own`
   - Test: `packages/core/test/ask-snapshots.test.ts` › `one need, one ask: a manager's two asks on the same target are two needs and two cards; each decision answers its own entry`
7. **The boot backfill is idempotent.** `backfillAsks` (World construction) writes the need of every open proposal (not a countered one: it waits on its manager), held grant and open request that has none, and files the ask of every asked retainer, pending captain and access request; a second run creates nothing.
   - Test: `packages/core/test/asks.test.ts` › `backfill files the asks and needs of everything already open, and a second run creates nothing`
8. **An author's ask card is refused only for missing structure; style rules are warnings** (Mitchell, 1:1 mt_ewxnhs90cq decision 5, 2026-11-10: "i don't think we need the linter for text"). An author's card, a manager's `ask`, `propose_grant`'s card (the explorer's `ask`; without one the proposal is a need its manager renders) or the Planner's `calibrate` card, is refused every time it lacks structure (`askStructure` in `packages/schema/src/ask.ts`, `refuseMissingStructure` in `packages/core/src/asks.ts`): two branches as buttons, the recommendation field, and its type's hard contract fields (money: prior decision, spent, steps; click: who is parked; credential: scope and fallback; meeting: the question; policy: the rule). There is no retry limit and no `ask.refused` event. Every other rule (sentence length, ids in the body, semicolons, parentheses, one instruction per sentence, condition first, ellipsis, dictionary words, and the soft contract fields: money claims, click permission, policy what-I-did and reversing cost) never refuses: `createAsk` files the card and records them as one `lint` history entry starting "warnings:", the author's answer names them, and no tag or pill marks the card. A retainer's, captain's or access request's card, written from its source's own words, is filed the same way.
   - Test: `packages/core/test/ask-contract.test.ts` › `structure is the hard contract fields, two branch buttons and the recommendation field; the rest only warns`
   - Test: `packages/core/test/ask-contract.test.ts` › `an author's card missing structure is refused every time; style rules file it with warnings in its history`
9. **A claim's check result is never older than 5 minutes when shown.** `GET /api/asks/:id` re-runs an ask's mechanical claims (`pr`, `url`, `api`, and `kr` when its howToCheck is a curl or a URL) whose result is missing or older than `CLAIM_STALE_MS` before it answers (`runClaimChecks`, `packages/core/src/ask-checks.ts`); the server also runs them in the background when an ask is filed. A check that cannot run is stored as a failed result with its reason, never thrown.
   - Test: `packages/server/test/asks.test.ts` › `lists open asks, records what a signed-in human opens (never an agent), re-runs a stale claim check on open, and decides and defers`
   - Test: `packages/core/test/ask-checks.test.ts` › `runs pr, url, api and kr checks, leaves manual alone, stores the results and goes stale after 5 minutes`
10. **No ask title or body contains an ellipsis.** A card is written for the reader and never quotes the record (docs/legible-delegation.md §5): a grant is named by its `title` (migration 105), never by its clipped objective. The linter's `no-ellipsis` rule warns on "…" in a title, body or recommendation. At boot `retitleClippedAsks` drops the clipping from every live card that still carries one, once, keeping its words, id, sources, rank and status.
   - Test: `packages/core/test/grant-title.test.ts` › `a live card with an ellipsis loses it and keeps its words, id, sources, rank and status; idempotent`
   - Test: `packages/core/test/grant-title.test.ts` › `refuses an ellipsis in an ask's title, body or recommendation`
11. **The Secretary's 1:1 carries the item open in the human's decision queue.** The queue PUTs the item on screen as the 1:1's `focus` (`PUT /api/meetings/:id/focus`, migration 106; only that 1:1's human, the same item twice writes nothing, null when the queue closes). Each of the human's lines reaches the agent with an "Open on <name>'s screen" block rebuilt from live data (`focusBlock`, `packages/core/src/meeting-focus.ts`): an ask decided or retired since it was opened says so, a gone id says gone. `act_in_1on1` with no target acts on that item, only on the human's cited words.
   - Test: `packages/core/test/meeting-focus.test.ts` › `listen carries the open item from live data: the ask's card, branches, status and target, then 'retired since it was opened'`
   - Test: `packages/core/test/meeting-focus.test.ts` › `act_in_1on1 with 'fund it' and no target decides the focused grant as the human`
   - Test: `packages/server/test/meeting-focus.test.ts` › `only the 1:1's human sets the open item; another human, an agent and a guest are refused; the same item twice is a no-op`
12. **Every live ask points at the entry that raised it** (`sourceEntryId`, migration 115; plan dc_uwx045472m step 6: an ask is a stored snapshot of a job's thread). A proposal's, a gate's, a request's, a retainer's, a captain or access request's and a rule's is its need (needs.ts, 1:1 mt_t65exni4et decisions 2 and 7), a manager's `ask` or pass-up the entry it wrote. A new card with no entry is refused. At boot `rerenderAsks` names the entry of a live ask filed before the migration.
   - Test: `packages/core/test/ask-snapshots.test.ts` › `a proposal's ask: its need on the grant's job; a request's: its need entry; a retainer's: its need on the retainer's job; a join request's: its need on the Town Hall's thread`
   - Test: `packages/core/test/ask-snapshots.test.ts` › `boot: a live ask filed before migration 115 gets the entry it came from, once`
13. **The town never writes words on a card; a card is marked when its thread moves** (1:1 mt_t65exni4et decision 2 point 2). `rerenderAsks` only names a missing source entry and a missing `renderedSeq`. A card keeps its author's or the Secretary's words; `entriesSinceCard` counts how far its thread has moved, the Secretary's `rank` read marks it THREAD MOVED, and `rank` `rewrite` (the Secretary only) writes its title, body or recommendation again, never its type, branches or target.
   - Test: `packages/core/test/ask-snapshots.test.ts` › `the town never writes words on a card: the request changes and the thread moves, the card keeps its words and is marked behind`
   - Test: `packages/core/test/ask-snapshots.test.ts` › `an author's card keeps its words and is marked behind its thread; the Secretary's read says so, and rewrite writes it again`
14. **A request for a human is a do ask: Done or Decline, never Claim, and it sorts last** (1:1 mt_msnjkpgwdb decisions 16-17). `request_human` needs `worth`; the `do` contract refuses a card without it; a boot repair (`requestsToDoAsks`) reopens claimed requests and rewrites their asks; an unranked do ask sorts after every other unranked ask; the Secretary may not close one as overtaken.
   - Test: `packages/core/test/asks.test.ts` › `boot repair: a claimed request is open again and its ask offers Done / Decline as a do; a second run changes nothing`
   - Test: `packages/core/test/asks.test.ts` › `an unranked do ask sorts after every other unranked ask, whatever its age`
   - Test: `packages/core/test/verbs.test.ts` › `open → done (no claim: 1:1 mt_msnjkpgwdb decision 17) creates a library human-report, answers its entry on the thread and notifies the agent`
15. **A human's decision on an ask wakes one Secretary run, debounced; an agent's act wakes none.** `decideAsk`, and `retireAsks` when a human's decision retired the ask, call `Secretary.afterDecision` (packages/core/src/secretary.ts): one pending run at a time, a line added per decision while it waits, at most `DECISION_RUNS_PER_DAY` a day, none while the ranking retainer is not approved, the Secretary is stopped or no ask is left open (1:1 mt_msnjkpgwdb decision 10).
   - Test: `packages/core/test/secretary-decisions.test.ts` › `the first decision queues one run on the ranking retainer that waits out the debounce; decisions meanwhile add a line, not a run`
   - Test: `packages/core/test/secretary-decisions.test.ts` › `a decision while a run is under way queues one more; nothing is queued with the retainer unapproved, the Secretary stopped, or no ask left open`
   - Test: `packages/core/test/secretary-decisions.test.ts` › `at most DECISION_RUNS_PER_DAY runs a day draw on the ranking retainer: past the cap a decision waits for the next ranking`
   - Test: `packages/core/test/secretary-decisions.test.ts` › `an agent's or the town's act is not a human decision: a manager withdrawing its proposal queues nothing`
16. **The Secretary closes only a click or policy ask as overtaken, never a money, credential or meeting ask nor a request a human must carry out**, and what it closes its building hears on its thread. `maySettle` and `overtakeCandidates` (packages/core/src/overtake.ts) are pure; `overtakeAsk` (packages/core/src/asks.ts) is the only writer, and a call that names one ask it may not close changes nothing (decisions 10 and 20a).
   - Test: `packages/core/test/overtake.test.ts` › `maySettle: only a live click or policy ask that is not a request a human must carry out`
   - Test: `packages/core/test/overtake.test.ts` › `property: every candidate is settleable, is not the decided ask, and is tied to the decision (same item, or names it)`
   - Test: `packages/core/test/secretary-decisions.test.ts` › `overtaken closes a click ask with the note, tells its building on its thread, and reopens what was deferred behind it; one call can also re-rank`
   - Test: `packages/core/test/secretary-decisions.test.ts` › `it never closes a money, credential or meeting ask, nor a request a human must carry out; a refused call changes nothing`
17. **A proposal, a gate and a request write a need, never a card; only a manager or the Secretary renders it** (1:1 mt_t65exni4et decision 2; `packages/core/src/needs.ts`). The need is an entry at level human on the job's thread; it is open until the target's deciding event answers it or a newer need supersedes it. While no live ask is on its target it sits in its manager's in-tray (`managerQueue`). `ask` on its target renders it with the need's type and branches and files no second entry; past `NEED_BACKSTOP_MS` the Secretary renders it with `rank` `render` and the manager is told. Free tokens count an open proposal by the grant, rendered or not. The human's decision entry carries the card they saw. At boot `templateCardsToNeeds` takes back live template cards; a rewritten or author card stays. Until its ask exists a need is no decision queue item and no deck slide (decision 3: only asks enter them): a proposed or held grant, an asked retainer, a captain or join request shows as one plain line with nothing to press ("Proposal from Prod: its card is being written."), under the queue (`cardsBeingWritten`, `packages/web/src/panels/queueOrder.ts`) and on the deck's state-of-the-town slide.
   - Test: `packages/core/test/review-deck.test.ts` › `a proposal with no ask yet is no slide, only one plain line on the town slide; its ask puts it on a slide (mt_t65exni4et decision 3)`
   - Test: `packages/core/test/needs.test.ts` › `a proposal writes a need and no card; it waits in the manager's in-tray and prompt until the manager renders it with ask`
   - Test: `packages/core/test/needs.test.ts` › `backstop: a need unrendered for an hour is listed in the Secretary read; rank render files the card and tells the manager`
   - Test: `packages/core/test/needs.test.ts` › `the human's decision on a rendered request keeps the card they saw on the thread, beside their words`
   - Test: `packages/core/test/needs.test.ts` › `boot migration: a live template card leaves the queue and its need waits for the manager; a rewritten card or an author's keeps its words; idempotent`
   - Test: `packages/core/test/free-tokens.test.ts` › `an open proposal claims its tokens by its need, before any card renders it (1:1 mt_t65exni4et decision 2 point 4)`
18. **The ask verb is the one entry point to the decision queue** (1:1 mt_t65exni4et decisions 7-8). Every card is filed by `packages/core/src/ask-verb.ts`: `askHumans` (the `ask` verb), `passUpWithAsk` (`review` with `ask`), `renderNeed` (a need rendered by its manager, by `propose_grant` with `ask` or by the Secretary's `rank` `render`) and `askOnOwnNeed` (the Planner's calibration and the Secretary's ledger rule write their need and render it at once). So `vetted` runs on every card. A retainer asked writes a need its building's manager renders. A captain or access request writes a need on the Town Hall's thread, which the Secretary renders at its next run with no hour's wait. `createAsk`, the asks table insert, is used only there. The code lint is an architecture test in `npm run check`: it fails any other source file that names `createAsk`, parses a new `Ask`, mints an `ak_` id or inserts into `asks`, and any test but the `seedAsk` seam in `packages/core/test/helpers.ts`.
   - Test: `packages/core/test/ask-entry-point.test.ts` › `no source file but ask-verb.ts names createAsk or inserts a new ask row`
   - Test: `packages/core/test/ask-entry-point.test.ts` › `ask-verb.ts holds the insert, and only the seedAsk helper seeds asks in tests`
   - Test: `packages/core/test/asks.test.ts` › `a checkpoint, a retainer, an outbox request, a captain ask and an access request each file one ask, and the event that decides each retires it`
19. **The rewrite rate is measured** (decision 9). `legibleMeasures` (`legible` on `/api/health` and `/api/town`) carries `cardRewrites`: over 14 days, the cards filed, those filed with style warnings, those the Secretary rewrote, and the rewrite rate overall, per building and per ask type. A rising rate says the manager's Asks paragraph is wrong.

20. **One need, one ask; nothing appends to a card** (1:1 mt_dwsxo7oms8 decisions 2-3). A card is written whole, from its thread, by one author at one time. `createAsk`'s door keys on the entry an ask views (`sourceEntryId`), and for the town's own needs on the live card of the same type on the same target that views no need of another kind and is no manager's `ask` entry (`liveAskForNeed`, needs.ts). A second ask on a keyed need makes no card and changes none: its words are one `ask-refused` entry on the card's thread (once), the card is marked behind, and the call fails with an error naming the live ask and how to rewrite it (`secondCardRefused`: the `ask` verb throws after the entry commits; `review` with `ask`, `propose_grant`'s card, the Secretary's render and code's own card roll back and write nothing). `createAsk` itself still returns the first ask with `folded: true` (decision-5 audit rank 1, grant gr_eztubyh7nf). Only a town placeholder (no recommendation, or missing structure) is replaced, whole, by an author's card. A manager's ask on a target is its own need: a credential beside a proposal is a second card, and `fileNeed` supersedes only an older need of the same kind. The card has no sources list; the thread is the list. A manager writes its own building's card again whole (`ask` with `askId`: title, body and recommendation together, structure refused, style warned) or withdraws it with a note (`withdraw`: status retired, its `ask` entry answered, nobody woken); another building's is refused. The Secretary's `rank` `fold` puts a dupe raised on another job in status folded with `foldedInto`; the human's decision on the survivor is written on both threads. No ask row is deleted.
   - Test: `packages/core/test/duplicate-asks.test.ts` › `a second ask on the same need entry (no target) returns the first with folded: true, writes one thread entry and leaves the card as it was`
   - Test: `packages/core/test/duplicate-asks.test.ts` › `a second ask on a grant with a live card is refused with an error naming the open ask; its words are one entry, the card is not glued`
   - Test: `packages/core/test/duplicate-asks.test.ts` › `a grant can carry a credential need and the town's proposal need at once: two cards, and a newer need of another kind supersedes nothing`
   - Test: `packages/core/test/duplicate-asks.test.ts` › `rewrites its own building's ask whole (lint still runs) and is refused on another building's`
   - Test: `packages/core/test/duplicate-asks.test.ts` › `withdraw retires the ask with the note, answers its own entry and wakes nobody`
   - Test: `packages/core/test/duplicate-asks.test.ts` › `fold: the later ask goes folded into the survivor, its thread says so; the human's decision lands on both threads`

21. **A goal proposal is a thread entry followed by its need** (1:1 mt_dwsxo7oms8 decision 4). `propose_goal` (goals.ts `propose`) writes the `gp_` row, then `fileGoalProposal` (needs.ts) writes the proposal as an entry on the proposer's thread (`jb_<building>`, the Town Hall's for the Planner and humans; `en_<gp>`, kind `goal-proposal`) and its need right after it (`en_<gp>_need`, kind `goal`, target kind `goalProposal`, a policy ask with Accept / Edit and accept / Cut), in one transaction; a missing thread is an error that names it. Nothing writes its card by code: the manager renders it with `ask` (the Secretary after the hour). A policy card on a goal proposal states the change (a `Change:` line, or a sentence naming the goal or key result) in place of a rule. The decision is `decideProposal` (`POST /api/goal-proposals/:id/decide`): it edits the tree, retires the ask and answers the need with the card the human saw; `decideAsk` on its ask is refused. A newer proposal on the same target retires the older one's ask and need. No open goal proposal is a Town Hall in-tray item, a badge count or a deck slide of its own. Boot (`backfillAsks`) gives an open proposal filed before this its entry and need, once.

   - Test: `packages/core/test/goal-proposal-thread.test.ts` › `Edit and accept: the human's decision edits the tree, answers the need on the thread with the card they saw and retires the ask`
